# DECISIONS — выбор стека и версии

## Архитектура

Клиент-серверная: SPA (Vite+React+TS) на GitHub Pages обращается по HTTPS к
REST API (Express) на Railway. Раньше (черновая версия) всё хранилось локально
в IndexedDB — отказались от этого в пользу настоящего бэкенда, т.к. финальная
постановка задачи требует деплоя фронтенда на GH Pages + бэкенда на отдельном
хостинге и CI/CD поверх этого. Изначально для бэкенда планировался Render, но
он требует обязательную верификацию банковской карты даже на бесплатном
тарифе, и карта не прошла подтверждение — перешли на Railway как
функционально эквивалентную альтернативу (тоже автодеплой из GitHub-репо,
тоже обычный Node-сервер, но без обязательной привязки карты).

## Фронтенд

- **Vite + React + TypeScript** — быстрый дев-сервер/HMR, прод-сборка в
  статические ассеты — то, что и нужно для GitHub Pages.
- **MUI** — готовые компоненты (Table, Dialog, TextField) с базовой
  доступностью из коробки.
- **Zustand** — минимальное глобальное состояние без boilerplate.
- **axios** — HTTP-клиент к бэкенду (`src/api/*`), единая точка для
  `baseURL`/обработки ошибок (в т.ч. 409-конфликтов).
- **date-fns** — форматирование дат для отображения в локальной таймзоне.

## Бэкенд

- **Node.js + Express** — минимальный REST API без лишней инфраструктуры,
  быстро поднимается на Railway как обычный Node-сервис.
- Хранение — JSON-файл на диске (`server/data/store.json`), без полноценной
  СУБД: осознанное упрощение ради срока. На бесплатном тарифе Railway файловая
  система эфемерна (переживает рестарты процесса, но не переживает новый
  деплой) — для учебного проекта это приемлемо, для продакшена нужна настоящая
  БД (Postgres и т.п. — путь для дальнейшего развития).
- **cors** с белым списком origin через `FRONTEND_ORIGINS` — чтобы бэкенд
  принимал запросы именно с GitHub Pages (и с localhost при разработке), а не
  с произвольных сайтов.
- Проверка пересечений интервалов продублирована на сервере (`overlap.js`) —
  клиентская проверка только для мгновенной подсказки в форме, не является
  источником истины.

## CI/CD

- **GitHub Actions** (`.github/workflows/deploy.yml`): при пуше в `main` —
  установка зависимостей, юнит-тесты, сборка фронтенда (`vite build` с
  `BASE_PATH=/<repo>/` и `VITE_API_URL` из переменной репозитория), публикация
  `app/dist` на GitHub Pages через официальные `upload-pages-artifact` /
  `deploy-pages`.
- **Railway**: бэкенд подключён к тому же GitHub-репозиторию (Root Directory =
  `server`) — при пуше в `main` Railway сам подтягивает изменения, ставит
  зависимости и перезапускает сервис. Отдельного workflow для бэкенда не
  требуется — это задача самого Railway, не GitHub Actions.

## Время

Хранение — UTC (ISO-8601), отображение/ввод — локальная таймзона браузера
(`app/src/utils/datetime.ts`), независимо от локали ОС/браузера.
